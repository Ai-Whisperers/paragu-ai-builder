# Tracing

Two parts: **correlation IDs** that propagate through every request so a single user interaction can be traced end-to-end, and **Sentry** for error grouping, release tracking, and performance.

---

## Correlation IDs

Every request carries a **trace id** that links all log lines, metric emissions, and downstream integration calls belonging to that request.

### Sources (in order of precedence)

1. Upstream `traceparent` header (W3C format: `00-<trace-id>-<span-id>-<flags>`)
2. Upstream `x-request-id` header
3. Upstream `x-correlation-id` header
4. Fresh UUID generated by `middleware.ts`

Implementation: [`web/lib/obs/request-id.ts`](../../web/lib/obs/request-id.ts). Middleware normalizes to `traceparent` + `x-request-id` on both the inbound request headers and the outbound response.

This means:
- Traces survive CDN / gateway / partner-integration hops if upstream supplies the id.
- A user filing a bug can quote the `x-request-id` from their browser's DevTools, and you can pull every log line for that request from Axiom with one query.

### Propagation within a request

[`web/lib/obs/context.ts`](../../web/lib/obs/context.ts) uses [Node's AsyncLocalStorage](https://nodejs.org/api/async_context.html) to thread the trace context through any code called during a request — no need to pass `requestId` through every function signature.

```ts
import { getRequestContext } from '@/lib/obs/context'

const ctx = getRequestContext()        // { traceId, businessId, locale, ... }
logger.info('event', { /* ctx auto-merged via logger */ })
```

The logger (see [logging.md](./logging.md)) reads from ALS automatically, so `trace.id` / `labels.business_id` / `labels.site_slug` appear on every log line inside the request without the caller threading them in.

## Sentry

**Why Sentry and not just logs?** Error grouping, deduplication, release tracking, source-map unwinding, assignee + alert routing. Logs tell you a thing happened; Sentry tells you "this is error #47, here are the 200 sessions affected, introduced in release `abc123`, assigned to Maya."

### Setup

1. Create a Sentry project (Next.js template).
2. Add to environment (local `.env.local` and production secrets):

   ```bash
   NEXT_PUBLIC_SENTRY_DSN=https://<public-key>@<org>.ingest.sentry.io/<project>
   SENTRY_TRACES_SAMPLE_RATE=0.1                 # server performance traces
   NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE=0.1     # browser performance traces
   NEXT_PUBLIC_SENTRY_REPLAYS_SESSION_RATE=0.1   # session replay (10%)
   ```

3. Deploy. [`web/instrumentation.ts`](../../web/instrumentation.ts) boots Sentry server-side on the first request; [`web/instrumentation-client.ts`](../../web/instrumentation-client.ts) boots it in the browser. **Without a DSN, both are no-ops — no change to local dev.**

### What gets captured

| Source | Mechanism |
|---|---|
| Server render errors | `onRequestError` hook in `instrumentation.ts` |
| Unhandled API route errors | `withRequestLog` catches + `captureException` with route tag |
| Client render errors | `app/error.tsx`, `app/global-error.tsx`, `[business]/error.tsx`, `s/[locale]/[site]/error.tsx` all call `captureException` |
| Manual captures | `import { captureException } from '@/lib/obs/sentry'` |

**Warn/info logs do NOT ship to Sentry** — they stay in the log pipeline (see [logging.md](./logging.md)). Only unhandled exceptions and explicitly captured events do.

### Performance tracing

Sentry performance gives basic spans for free — page transactions, API route latency, DB calls (when instrumented). The 10 % default sample rate is plenty for finding p95 regressions.

Sample rates are tuned via the env vars above; see [`web/lib/obs/sample.ts`](../../web/lib/obs/sample.ts) for the shared strategy.

### Session replay

10 % of sessions are replayed by default. Replay links appear on associated error events in the Sentry UI — drastically speeds up "what did the user click before the crash" investigations.

Cost optimisation: drop session-rate to 0 % and set error-replay-rate to 100 % so you only pay for replays of sessions that actually errored. See [README.md § future work](./README.md#future-work).

### Cost

Free tier: 5 000 errors + 10 000 performance transactions + 50 replays per month. At current volume that's plenty of headroom.

## End-to-end trace example

User submits a lead on `nexaparaguay.com/contacto`. You want every log line + Sentry event + metric emission for that submission.

1. Browser DevTools → Network tab → response headers → copy `x-request-id` (e.g. `abc-123-def-456`).
2. In Axiom (see [logging.md](./logging.md#option-a--axiom-recommended)):

   ```apl
   ['paragu-ai-builder-logs']
   | where ['trace.id'] == 'abc-123-def-456'
   | sort by _time asc
   ```
3. In Sentry → search bar → `trace:abc-123-def-456` to see any associated errors + performance spans.
4. In Analytics Engine (see [metrics.md](./metrics.md)) → filter metric rows by the same trace id for the emitted counters.

All three sinks share the same id because `middleware.ts` writes it to logger ALS, Sentry tags, and the metrics writer on every request.
